# 作品恢复

2026-09-19，仓库迭代 0.4.0。

## 为什么先做恢复

原有流程可导出作品包，却不能导回。作者更换浏览器或清理浏览器存储后，只能手工复制稿件，逐条采纳与撤销记录无法继续使用。这个缺口直接影响持续创作，优先级高于增加生成按钮或装饰动效。

用户动作保持简单：创作库导出 JSON，在另一处启动本地网页，导入，再保存。外部作品始终作为新副本打开，文件里的作品编号不会覆盖本机已有作品。未保存的内容只有在校验成功且用户明确同意替换后才被替换。文件损坏、请求失败和取消替换保留当前输入及修订状态。

## 数据如何恢复

`schemas/project.schema.json` 定义版本 1.0。兼容旧版没有版本字段的作品包；未知版本拒绝导入。四类任务的输入、要求、建议、选择和撤销快照分开保存。单个作品包最多 8,000,000 字节，最多 12 张插图，图片 data URL 合计最多 2,000,000 字符。

`POST /api/project/validate` 在本机运行，不写文件、不调用模型。它校验结构、任务、输入指纹、原文定位和选择编号，丢弃缓存稿件、Markdown、编辑位置和请求内容，再通过既有 session 引擎重建。撤销快照中的编号也必须属于该建议包。它检查结构一致性，不证明记录的身份、创作时间、文学质量或历史真实性。

如果作者修改了当前原稿或要求，旧评审仍可恢复，但不会生成可导出的当前结果；恢复与建议绑定的输入后可继续审阅。没有有效建议的草稿和只准备了请求的作品也能恢复。

插图必须内嵌为 PNG、JPEG、WebP 或 GIF。拒绝外部网址、SVG、不合法 base64、重复编号及与文件头不匹配的格式。基础文件头检查不是完整图片解码器。浏览器用 DOM 属性设置图片和文件名，不把导入字段拼成 HTML。

## 已执行的验收

- Python 回归覆盖原稿保留、选择重建、缓存篡改、撤销编号、输入过期、旧包兼容、图片格式和真实 HTTP 边界。
- 1440 与 390 宽度真实浏览器：导出后关闭整个浏览器上下文，在空白存储的新上下文导入，再核对原稿、选中稿件、图片和两步撤销。
- 同一包重复导入后保存产生新编号，本机原作品仍在。损坏 JSON、无效撤销记录、网络失败和用户取消均保留当前草稿。
- 导入校验期间输入与替换控件禁用。恢复的过期建议禁止导出，恢复原始输入后才可继续。
- 导出正文与选择结果一致；无横向溢出、脚本异常或指定 axe 自动检查违规。插图板收起后不再保留大块空白。

复现：`python -m unittest discover -s tests -v` 和 `npm run test:review`。浏览器结果见 [project-recovery.json](evaluation/project-recovery.json)，CI 上传完整截图与报告。全部材料为仓库原创虚构案例，没有使用私人作品。

## 下一步如何验证价值

真实作者测试尚未执行。让作者完成一次“采纳两条、保留一条、导出、换浏览器恢复、撤销并继续修改”的任务，观察是否需要帮助、恢复后数据是否一致以及耗时。恢复成功率分母为开始恢复的任务数，失败包含文件选择、校验、保留记录或继续编辑任一步无法完成。比较手工复制流程，不能用开发者回归通过率代替真实作者效果。

不提供云备份、加密、多设备自动同步或多人合并。作品包是明文，导入依赖本地服务。网页文本框沿用浏览器的换行规范；要求保留原文件 CRLF 字节时使用 CLI。

# 从用户问题到交付

这是产品设计假设与本地实现案例，不是用户研究结论或线上业绩。目标是让评审者可以沿着用户任务、设计取舍、源码和验证记录追问。

## 用户为什么需要它

目标用户：希望保持自己表达方式的小说创作者。触发时刻：大纲或局部段落卡住，既想获得帮助又不愿丢失原稿与创作主导权。

用户真正要完成的事：尝试不同修订方向并选择保留哪一个。价值发生在这个任务完成时，不发生在模型输出字数增加时。

现有替代：通用聊天将创作与版本管理割裂，复制粘贴容易覆盖原稿。差异化假设应通过真实任务对照验证，不能用功能数量或模型名称代替。

## 用户会怎么使用

创建作品 → 选择大纲或局部任务 → 输入草稿 → 审阅建议 → 保留原稿 → 保存或导出。

首次使用以示例降低输入成本，再让用户带着自己的合规资料使用。每个处理中状态必须对应真实请求；失败保留输入，结果可复查、可导出。成功不是点击生成，而是用户能做下一步决定。

## 产品定义与技术分工

宿主模型提供生成辅助；当前本地模板用于可控展示结构，明确未连接LLM。

关键取舍：输出按任务隔离；覆盖未保存草稿需确认；本地保存失败仍可导出。最重要的失败模式：模板化生成不能证明文学质量；不同作者对有效建议的判断高度主观。

界面/交互入口：[web/index.html](../web/index.html)。实现入口：[scripts/plugin_run.py](../scripts/plugin_run.py)。

## 指标定义

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 任务价值 | 用户采纳或进一步编辑的建议比例；分母为用户实际阅读的建议数 | 自愿参与的任务测试与人工标注 |
| 使用效率 | 从开始有效输入到完成核心动作的中位时长 | 本地计时，不收集原始问题正文 |
| 质量护栏 | 草稿丢失次数、非自愿覆盖数、风格模仿请求拦截、保存失败率 | 固定回归集和人工抽查 |
| 可用性 | 请求成功率、P95处理延迟、输入恢复成功率 | 去标识事件与运行日志 |

当前没有线上用户基线，不报告增长率或客户收益。先采集基线，再预注册改善目标，避免看完数据再选成功指标。事件字段契约见 metrics.schema.json；它是接入设计，不代表已有生产遥测。

## 价值验证计划

让作者在原创虚构片段上测试修订任务，记录保留/改写/拒绝原因与恢复原稿的成功率；不使用真实私人作品。建议首轮覆盖 5 名目标用户用于发现可用性问题，不以该样本估计市场效果。记录任务前提、失败位置和原话；未执行前均为计划。

技术回归与用户验收分开：Schema通过只能证明结构；构建通过只能证明可构建；虚构检索集通过只能证明小样本链路；真实任务成功才支持用户价值。

## 迭代顺序

1. 当前版本：建立明确输入/输出、失败恢复、示例、测试和可审阅文档。
2. 下一版本：增加段落级diff与版本恢复，然后用作者偏好评估选择可选模型适配器。
3. 扩展条件：只有核心任务通过且护栏没有恶化，再扩展自动化、数据源或模型。

## 面试时可以展示

先用一个具体任务展示入口与失败状态，再打开设计取舍和测试，解释为什么某些步骤用规则、另一些步骤需要模型。展示本地证据，同时明确线上部署、客户收益和专业有效性未获验证。

外部组件解决通用技术问题；本项目的可归属贡献是问题定义、流程设计、约束、接口集成和验证，不把开源模型能力说成自研算法。
